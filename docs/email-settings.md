# Form email notifications

In Admin → Settings → Email Settings, enter the SMTP hostname, port, connection
security, mailbox username, mailbox/app password, sender name and sender address.
Add the notification recipients and optional CC addresses, separated by commas.
Use **Save Email Settings**, then **Send Test Email**. Testing works while
notifications are disabled. Enable notifications and save when ready.

Demo, contact and custom forms use the main recipient list. The optional **Send
career notifications to** field replaces the main To list for career applications;
leaving it blank preserves the main recipients. The shared CC list still applies,
and the same SMTP sender and password are used. Career forms are identified by
the saved form slug/name containing "career", "careers" or "job application".
Send Test Email checks the main To and CC addresses.
Old per-form recipient values are retained in the database for
compatibility but are no longer used for delivery. SMTP environment variables are
no longer used; configure this panel after deploying the change.

Each notification contains the submitted fields, form/source, lead ID and uploaded
file download links. Replies use the submitter's email when available. A successful
SMTP response means the server accepted the message, not guaranteed inbox delivery.
Check spam folders and the provider's delivery logs if needed.

The shared submission route stores the lead before attempting email. Disabled or
failed email does not remove the lead or fail the submission. Failures are logged
with the lead ID and a sanitized error. There is no automatic retry or resend of
historical leads in this change.

## Google Workspace (formerly G Suite)

The client's mailboxes are hosted by Google Workspace. Enter:

- SMTP server: `smtp.gmail.com`
- Port: `587`
- Connection security: `STARTTLS`
- Username and sender email: the full Workspace mailbox address
- Password: a Google App Password generated by the mailbox owner
- To and CC: the client's chosen notification recipients

The client enables 2-Step Verification on the sending Google account and generates
an App Password, then enters it directly in the admin panel. They do not need to
share it with the development team. Do not use the normal Google account password.
If App Passwords are unavailable, the Workspace administrator must review the account
policy. This implementation supports SMTP app-password authentication; OAuth-only
accounts need a separate OAuth integration or an approved relay configuration.

Save the settings and use Send Test Email to verify acceptance and inbox delivery.
SSL/TLS on port `465` is also supported if selected together.

- [Google Workspace SMTP setup](https://support.google.com/a/answer/176600)
- [Google App Password instructions](https://support.google.com/accounts/answer/185833)

## Storage and deployment

No database migration is needed. The existing `site_settings` table stores a
separate `email_private` record. The public settings endpoint reads only the `site`
record. Only authenticated admin endpoints can read or update email configuration;
they return a password-presence flag, never the password or its ciphertext.

The password uses AES-256-GCM with a dedicated HKDF-derived key. Key material comes
from `EMAIL_SETTINGS_ENCRYPTION_KEY`, if provided, otherwise the already-required
`JWT_SECRET`. Keep it stable across deployments. Changing either effective key
requires re-entering the SMTP password in the admin panel. A dedicated encryption
key can be set before initial configuration to separate it from session key rotation.
Do not put mailbox credentials into source files or public frontend environment variables.
